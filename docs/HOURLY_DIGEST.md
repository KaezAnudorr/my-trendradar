# 每小时更新与 22:00 总结

## 日常用法

本机打开 http://127.0.0.1:8765/current.html 。Actions 按北京时间每小时第 7 分钟错峰抓取（22 点单独在 22:00 触发），保留完整热榜和 RSS，并与已推送记录比对；没有新增时不发送消息。首次启用只建立基线，避免一次补推几百条旧内容。

本机预览服务每分钟检查最新报告，内容不变就不改本地文件；页面每 30 秒检查本地版本，仅新版本出现时自动刷新。电脑或预览服务关闭期间，本机页面不会自动更新；云端抓取、飞书和 AI 调度继续执行。

## 北京时间每天 22:00

- 时间窗口为 22:00–23:00，AI 与总结推送各执行一次。
- 汇总当天累计抓到的新闻，不只看 22 点仍在榜的内容。
- 使用每批 200 条的分批分析，再综合各批摘要，覆盖完整输入，不再截取前 150 条。
- 晚间只推 AI 综合总结，不再把全天新闻列表重复推一遍。
- 首日从启用持久化后的第一次抓取开始累计，无法补回此前已下榜且未保存的新闻。
- GitHub cron 可能因排队延迟或高负载漏触发，22:00 是计划触发时间；未在 22:00–23:00 窗口启动时，当晚总结不会执行。普通抓取错开整点以降低高峰影响，不能作为严格准点服务。

## 为什么原来四个平台只有几条

现有热榜通过关键词筛选后才展示。这次取消热榜关键词过滤，各来源显示完整返回榜单，消息推送则由独立的已发送记录控制去重。保留按来源分组和 RSS 原来的文章时效规则。

DailyHotApi 提供 bilibili、weibo、douyin、zhihu 四条接口；每次准备数据时做实际请求验证。微博、抖音、知乎与现有接口相比，只有返回更多有效条目时才作为本轮同一榜单的替代；B站接口是视频排行榜，和原来的热搜词不同，因此作为额外“热门视频快照”订阅，不替换热搜词榜。

验证结果保存在 dailyhot-integration artifact 内的 four-apis.json。接口失败时保留既有来源，并在结果中写出失败原因。

## 跨次运行保留状态

每次运行恢复上一份 trendradar-state artifact，其中包括每天的 SQLite 数据和 push-state.json。成功推送后才记录文章身份，跨日不重复推旧消息；推送失败不写成功记录。数据库保留最近三天，状态 artifact 保留十四天。连续长于十四天没有成功运行时，旧 artifact 会过期，恢复后重新建立静默基线。

定时任务串行运行，不取消正在抓取和推送的上一轮。项目原有“每七天 Check In”机制仍然保留，到期需要运行 Check In 续期。

## 本机同步的数据位置

这不是 GitHub Pages 网站。Actions 把公开新闻报告更新到专用的 generated-preview 分支，本机服务从该分支读取，不需要在本机保存 GitHub token 或 AI 密钥。该分支只保存最新生成报告，由工作流整体替换，不用于手工编辑。

本机服务代码：tools/serve_preview.py。停止后用 Python 运行该脚本，并通过 --directory 指定本机报告目录，即可重新启动；默认端口为 8765。

## 修改和测试

- 调度：config/timeline.yaml 的 custom。
- 全量分析批大小：config/config.yaml 的 ai_analysis.max_news_for_analysis。
- 去重新消息：notification.new_only。
- 主工作流：.github/workflows/crawler.yml。
- 不调用付费 API 的验收：tests/test_hourly_digest.py，覆盖七天每小时的调度、首次基线、无新增静默、成功/失败记账、跨日去重、晚间只推总结、分批完整覆盖。
- 手动 Test AI and Feishu 仍是显式测试入口，会暂时关闭调度限制，立即调用 AI 并推送，和正常定时任务分开。
